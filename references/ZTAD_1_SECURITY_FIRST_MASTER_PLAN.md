## 0. Document Control

### 0.1 Normative language

The terms **MUST**, **MUST NOT**, **SHALL**, **SHALL NOT**, **SHOULD**, **SHOULD NOT**, and **MAY** are used as control requirements.

- **Mandatory control:** Required before the related risk class may be automated.
- **Initial policy:** A safe starting threshold that MUST be calibrated using real delivery data.
- **Advisory practice:** Recommended but not itself a release gate.
- **Human decision:** A decision made by an accountable person, not by a model.
- **Machine evidence:** Evidence generated by a trusted tool or protected CI/CD control plane and bound to an exact source revision or artifact digest.
- **Agent claim:** A model-generated statement. It is never authoritative by itself.

### 0.2 Decision status

| Decision | Status |
|---|---|
| Use a deterministic control plane rather than an LLM orchestrator | Mandatory |
| Treat all model output as untrusted proposals | Mandatory |
| Use one implementation model and one independent review model for R1–R3 behavioral changes | Approved baseline |
| Use a third model only for architecture or unresolved escalation | Approved optional control |
| Require human approval for high and critical changes | Mandatory |
| Use Scrumban with continuous delivery rather than sprint-batched releases | Approved baseline |
| Bind all test, review, build, and deployment evidence to exact SHAs or digests | Mandatory |
| Separate application, delivery-control, and production-release authority | Mandatory for the High-Control profile |
| Initial numeric limits in this plan | Working thresholds; calibrate after sufficient data |

### 0.3 What this plan can and cannot guarantee

This system cannot guarantee that software will contain zero defects. No agent, reviewer, test suite, or process can prove the absence of every possible defect in a non-trivial system.

It is designed to provide the strongest practical controls for:

1. limiting agent authority;
2. preventing unsupported agent claims from becoming decisions;
3. detecting defects before release;
4. bounding the blast radius of escaped defects;
5. making releases reproducible and auditable;
6. stopping ambiguous or irreversible work before damage occurs; and
7. reducing token use without weakening required evidence.

The governing principle is:

> **Agents propose. Trusted tools produce evidence. Policy-as-code decides. Humans authorize high-risk exceptions.**

## 1. Executive Design

### 1.1 Target operating model

The target system is a **risk-adaptive Scrumban delivery system** with a **deterministic, zero-trust control plane**.

It consists of five planes:

1. **Product and governance plane**
   Owns outcomes, requirements, risk acceptance, and human approvals.

2. **Deterministic control plane**
   Owns the state machine, policy evaluation, budgets, evidence validation, and routing. It is not an LLM.

3. **Agent execution plane**
   Contains bounded implementation and review agents. Agents have no merge or production authority.

4. **Verification and supply-chain plane**
   Contains protected CI, tests, scanners, build provenance, SBOM generation, and artifact verification.

5. **Release and runtime plane**
   Promotes one verified artifact through staging and production, observes it, and rolls it back or stops rollout when required.

### 1.2 Recommended model topology

Normal delivery uses only two model roles:

| Role | Recommended assignment | Authority |
|---|---|---|
| Implementation Agent | Primary coding model in Codex, using an exact approved model/version | May edit an isolated worktree and run approved local tools |
| Independent Review Agent | A different model family, using an exact approved model/version | Read-only; may propose findings |
| Architecture/Escalation Advisor | Stronger model, invoked only by policy for R3/R4 or unresolved ambiguity | Advisory only; cannot approve |

A practical reference assignment is:

- **Implementation:** GPT-5.6 through Codex.
- **Independent review:** Claude Sonnet-class model.
- **Escalation:** Claude Opus-class model, only when the escalation policy fires.

A different model family is preferred for independent review because it diversifies failure modes. If organizational data policy prohibits a second provider, use a separately configured approved model with an isolated context and retain all deterministic and human gates. Model diversity is defense-in-depth, not proof.

These names are not permanent policy. The **Model Registry** must contain the exact approved model identifiers, prompt versions, evaluation results, and permitted risk classes. There must be no silent use of `latest` and no silent fallback to another model.

### 1.3 Hermes position

Hermes may be used as a worker router or user interface, but it SHALL NOT be the source of truth for:

- workflow state;
- risk classification;
- budgets;
- evidence validity;
- merge eligibility;
- deployment eligibility; or
- production status.

If Hermes uses an LLM internally, its decisions are agent claims. A deterministic wrapper must validate every requested transition and tool action.

### 1.4 Why the previous approach was insufficient

A workflow of “one model writes, another model reviews, a third model arbitrates” is not a sufficient control system because multiple models can:

- share the same incorrect assumption;
- agree on a hallucinated API or repository fact;
- accept a test that encodes the wrong behavior;
- overlook the same hidden coupling;
- be manipulated by repository content;
- report success for commands they did not actually run; or
- approve a revision different from the one eventually merged.

The corrected design never treats agreement among models as proof. Model diversity is used to improve defect discovery, not to authorize changes.

## 2. Objectives, Constraints, and Non-Goals

### 2.1 Primary objectives

The system SHALL optimize for all of the following, in this order:

1. safety and data integrity;
2. evidence-based correctness;
3. recoverability;
4. short feedback loops;
5. low change lead time;
6. efficient token use;
7. auditability;
8. low operational burden.

### 2.2 Constraints

- Agents are probabilistic and may confabulate.
- Repository content may contain accidental or malicious instructions.
- Tests may be incomplete, flaky, or intentionally weakened.
- Build and deployment infrastructure may be attacked.
- A solo developer may hold several human roles; technical separation must still be preserved through separate credentials, protected paths, and explicit gates.
- High control must not force every trivial change through the same expensive process.
- The system must support continuous deployment without waiting for sprint boundaries.
- The default must be fail-closed for security, permissions, data loss, financial logic, and irreversible operations.

### 2.3 Non-goals

The system is not intended to:

- make an LLM the product owner;
- allow agents to decide ambiguous business requirements;
- use model confidence as a release criterion;
- use majority voting among models as truth;
- provide fully autonomous R3 or R4 production changes;
- replace incident management, backups, or disaster recovery;
- maximize code volume or model activity;
- optimize token cost by skipping required controls;
- require long synchronous Agile ceremonies.

## 3. Threat and Failure Model

The controls in this plan SHALL address the following failure classes.

### 3.1 Agent reasoning failures

- fabricated files, functions, APIs, commands, test results, or deployment results;
- incorrect root-cause claims;
- incomplete impact analysis;
- unsupported “no side effects” claims;
- incorrect severity classification;
- stale assumptions from prior context;
- overfitting tests to the implementation;
- unnecessary refactoring and scope expansion;
- repeated repair loops without convergence;
- incorrect use of tools;
- instruction-following failures.

### 3.2 Agent security failures

- prompt injection from issues, code comments, logs, documentation, dependencies, or web content;
- secret exposure;
- code or data exfiltration;
- unauthorized network use;
- destructive shell commands;
- privilege escalation;
- misuse of MCP or plugin write tools;
- agent modification of its own policies, instructions, tests, or workflow gates;
- excessive agency caused by broad credentials or generic tools.

### 3.3 Software delivery failures

- broken builds;
- false-positive or false-negative tests;
- flaky tests;
- incompatible changes against the latest main branch;
- hidden API, event, database, or configuration coupling;
- vulnerable or compromised dependencies;
- mutable build inputs;
- build/release artifact mismatch;
- environment drift;
- failed or unsafe rollback;
- database migration failure;
- monitoring blind spots.

### 3.4 Governance and operational failures

- unclear ownership;
- ambiguous requirements;
- risk downgrade without evidence;
- unauthorized bypass;
- stale approval after a new commit;
- silent model or prompt changes;
- uncontrolled token loops;
- weak audit trail;
- exception or waiver without expiry;
- emergency changes that never receive retrospective review.

## 4. Core Control Principles

### 4.1 Untrusted-agent principle

Every model output SHALL be treated as untrusted input, including outputs from:

- the implementation model;
- the review model;
- an architecture model;
- a model acting as an orchestrator;
- a model used to summarize logs;
- a model used as a grader.

### 4.2 Separation of duties

No single agent or service SHALL be able to:

1. modify source code;
2. change the controlling policy;
3. mark its own evidence as valid;
4. merge the change; and
5. deploy it to production.

### 4.3 Least authority

Each role SHALL receive only the minimum capability required for its current task.

### 4.4 Evidence before authority

A state transition SHALL require machine evidence or an explicit human decision. Natural-language statements do not satisfy gates.

### 4.5 Exact-subject binding

Evidence SHALL be bound to:

- repository identity;
- approved Change Contract/specification hash;
- base SHA;
- head SHA;
- policy bundle hash;
- tool or workflow version;
- relevant environment or runner identity; and
- artifact digest where applicable.

### 4.6 Unknown means stop or escalate

The system SHALL never convert missing information into a positive assumption. Unknown or unverified conditions shall:

- escalate risk;
- request additional evidence;
- require human resolution; or
- block the workflow.

### 4.7 Small batches

Changes SHALL be sliced into the smallest independently testable and deployable unit that creates value or reduces risk.

### 4.8 Build once, promote by digest

Production SHALL receive the exact artifact that passed staging verification. The production workflow SHALL NOT rebuild source code.

### 4.9 No model-controlled policy

Risk, state transitions, permissions, budget enforcement, and release eligibility SHALL be implemented outside the model.

## 5. Target Architecture

```text
┌─────────────────────────────────────────────────────────────────────┐
│ Product and Governance Plane                                        │
│ Product Owner | Engineering Owner | Security Owner | Human Approver │
└──────────────────────────────┬──────────────────────────────────────┘
                               │ approved specification / decisions
┌──────────────────────────────▼──────────────────────────────────────┐
│ Deterministic Control Plane                                         │
│ State Machine | Policy Engine | Risk Engine | Budget Controller     │
│ Context Builder | Evidence Validator | Patch Broker | Audit Ledger   │
└───────────────┬────────────────────────────┬────────────────────────┘
                │ bounded task              │ validated evidence
┌───────────────▼─────────────────┐  ┌──────▼─────────────────────────┐
│ Agent Execution Plane            │  │ Verification / Supply Chain    │
│ Implementer: workspace-write     │  │ Protected CI, SAST, tests      │
│ Reviewer: read-only              │  │ SBOM, provenance, attestations │
│ Advisor: read-only               │  │ Immutable artifact registry    │
└───────────────┬─────────────────┘  └──────┬─────────────────────────┘
                │ patch proposal             │ verified digest
                └──────────────┬──────────────┘
                               │
┌──────────────────────────────▼──────────────────────────────────────┐
│ Release and Runtime Plane                                           │
│ Staging | Release Controller | Canary/Rings | Monitoring | Rollback │
└─────────────────────────────────────────────────────────────────────┘
```

### 5.1 Repository separation

The High-Control profile SHALL use at least three repositories or equivalent protected trust zones.

| Repository / trust zone | Contents | Agent write access |
|---|---|---:|
| Application repository | Product source and ordinary feature tests | Worktree only |
| Delivery-control repository | Reusable workflows, policies, schemas, protected test harnesses | None |
| Environment/release repository or protected release service | Approved artifact digests and environment configuration | None |

An append-only evidence store SHALL retain signed or hashed evidence records.

### 5.2 Why control-plane separation is mandatory

Keeping policies and application code in the same editable trust zone allows a change to weaken the controls that evaluate it. A separate delivery-control repository prevents an application agent from changing:

- required checks;
- test commands;
- coverage thresholds;
- workflow permissions;
- deployment logic;
- agent schemas;
- risk rules;
- evidence validators;
- release gates.

Reusable workflows and third-party actions SHALL be referenced by full immutable commit SHA.

### 5.3 Control-plane reliability

The control plane itself is production software and SHALL be engineered accordingly.

- State transitions SHALL be transactional or compare-and-swap protected.
- Every webhook, task, model call, patch submission, and deployment command SHALL carry an idempotency key.
- Duplicate events SHALL not duplicate commits, deployments, approvals, or rollbacks.
- Policy decisions SHALL record the exact policy bundle version.
- Audit events SHALL be tamper-evident through signatures, append-only storage, or hash chaining.
- If the State Machine, Policy Engine, or Evidence Validator is unavailable, merge and release gates fail closed.
- Agent work MAY continue locally during a control-plane outage, but it cannot progress into a trusted state.
- Backup and restore of workflow state and the evidence index SHALL be tested.
- Time synchronization SHALL be monitored because approvals, expiry, and evidence ordering depend on reliable timestamps.

### 5.4 Control-plane compromise and recovery

The control plane SHALL have an explicit compromise procedure. At minimum:

- signing, GitHub App, OIDC, and service identities are separately rotatable;
- administrative access uses strong authentication and is not shared with agent runtime identities;
- policy bundles, workflow revisions, and evidence signatures can be independently verified;
- a suspected compromise freezes merge and release while preserving read-only evidence access;
- trusted artifacts built during the suspected window are quarantined until re-verified;
- recovery starts from a known-good policy/workflow revision and clean credentials;
- a post-recovery review determines which evidence, approvals, and releases must be invalidated;
- the compromise scenario is exercised in a tabletop or recovery drill.

### 6.3 Solo-developer adaptation

When one person owns product, engineering, and security roles:

- separate service identities SHALL still be used;
- the agent SHALL still have no direct SCM or production credential;
- protected paths and environments SHALL remain enabled;
- R3/R4 releases SHALL require an explicit manual review of the evidence manifest;
- break-glass actions SHALL be separately logged;
- a waiting period MAY be required for irreversible R4 actions;
- an external human reviewer SHOULD be used for destructive migrations, authorization changes, or regulated financial logic.

## 7. Agile Operating Model

### 7.1 Framework selection

Use **Scrumban**:

- Scrum-style product goals and short planning horizons;
- Kanban visualization, WIP control, explicit flow policies, work-item age, and service-level expectations;
- continuous deployment as soon as Definition of Done is met;
- no requirement to wait until a sprint boundary.

### 7.2 Cadence

The process is async-first.

| Activity | Cadence | Purpose |
|---|---|---|
| Outcome and backlog replenishment | Weekly | Select the next small valuable items |
| Flow review | Daily, asynchronous | Check blocked work, age, and WIP |
| Product review | Weekly or on meaningful release | Validate user outcome |
| Delivery-system retrospective | Every two weeks initially, then monthly | Improve one measured bottleneck |
| Risk-policy review | Monthly and after serious incidents | Calibrate thresholds and overrides |
| Model/prompt review | On change and at least quarterly | Prevent silent drift |
| Recovery drill | Quarterly; more often for critical systems | Prove rollback and restore capability |

### 7.3 Board and WIP

```text
Backlog
→ Ready
→ Active
→ Machine Verification
→ Independent Review
→ Merge Queue
→ Release
→ Observe
→ Done
```

Initial WIP limits:

| State | Initial WIP limit per developer/product stream |
|---|---:|
| Active | 1 |
| Machine Verification | 2 |
| Independent Review | 2 |
| Merge Queue | Managed by repository capacity |
| Release / Observe | 1 production rollout per service |

The expedite lane SHALL have a maximum WIP of one and SHALL be limited to active incidents or verified urgent security exposure.

### 7.4 Work-item classes

| Class | Use |
|---|---|
| Standard | Normal product and technical work |
| Fixed date | Legitimate external deadline |
| Expedite | Active incident, exploitable vulnerability, or severe service interruption |
| Intangible | Risk reduction, maintainability, or prevention work |

### 7.5 Service-level expectations

SLEs are forecasts, not promises. Initial SLEs SHALL be replaced by historical percentiles after at least 30 comparable completed work items.

Suggested initial targets:

| Risk | Initial target |
|---|---|
| R0 | 85% completed within one business day |
| R1 | 85% completed within two business days |
| R2 | 85% completed within five business days |
| R3 | Planned individually; target less than ten business days where feasible |
| R4 | No generic SLE; governed by an approved change plan |

### 7.6 Small-batch policy

An item SHALL be split or escalated when it exceeds the initial change envelope.

| Risk | Logical changed LOC* | Product files* | Services | Action when exceeded |
|---|---:|---:|---:|---|
| R0 | 80 | 3 | 0–1 | Reclassify |
| R1 | 150 | 6 | 1 | Split or R2 |
| R2 | 300 | 10 | 1 | Split or R3 |
| R3 | 600 | 20 | Up to 2 | Human re-scope |
| R4 | Approved plan | Approved plan | Any | Explicit architecture and release plan |

\* Generated code, lockfiles, snapshots, and vendored files are counted separately by policy and do not hide a large behavioral change.

These are initial guardrails, not universal truths. Historical defect and flow data SHALL be used to tune them.


### 8.2 Requirement authority

The model MAY:

- normalize wording;
- identify ambiguity;
- propose acceptance criteria;
- propose edge cases;
- propose invariants;
- propose a risk escalation.

The model SHALL NOT:

- invent a business decision;
- silently resolve conflicting requirements;
- remove an acceptance criterion;
- weaken an invariant;
- change a regulatory interpretation;
- downgrade risk.

When the specification is materially ambiguous, the only valid result is:

```text
SPEC_BLOCKED
```

The response SHALL identify the exact ambiguity and the decision owner.

### 8.3 Definition of Ready

A work item is `READY` only when:

- outcome and owner are known;
- acceptance criteria are testable;
- non-goals are explicit;
- relevant invariants are identified;
- applicable security, privacy, performance, availability, accessibility, and compatibility requirements are explicit;
- data classification and service criticality are known;
- unknown assumptions are either resolved or represented as blocking;
- initial affected components are identified;
- a test oracle exists;
- rollback approach is plausible;
- observability is defined;
- the deterministic risk engine has run;
- the change is within the size envelope or has an approved split;
- required human plan approval has been obtained for R3/R4.

## 9. Deterministic Risk Engine

### 9.1 Authority

The Risk Engine SHALL be code, not an LLM. It SHALL run twice:

1. **Pre-implementation classification** from the intended scope, requirements, and declared components.
2. **Post-patch classification** from the actual diff, AST/schema changes, manifests, and generated impact graph.

The final risk is the higher of the two results plus any hard override or escalation. It SHALL calculate the minimum risk from:

- changed paths;
- AST or schema changes;
- dependency manifest changes;
- permissions and policy changes;
- database migration operations;
- infrastructure changes;
- public API or event-contract changes;
- user and tenant blast radius;
- reversibility;
- test maturity;
- operational novelty;
- data classification;
- financial or regulatory impact.

An agent MAY only request escalation. It cannot reduce risk.

### 9.2 Score

The initial scoring model uses seven dimensions.

| Dimension | Range | Example maximum |
|---|---:|---|
| User/service impact | 0–3 | Broad outage or critical flow |
| Data/security/privacy impact | 0–4 | Sensitive data or authorization |
| Financial/regulatory impact | 0–4 | Payments, taxes, compliance |
| Reversibility | 0–3 | Destructive or irreversible |
| Blast radius/coupling | 0–3 | Multiple services or tenants |
| Verification maturity | 0–3 | Weak oracle or poor test coverage |
| Operational novelty | 0–2 | New runtime, dependency, or deployment method |

Initial mapping:

| Score | Minimum risk |
|---:|---|
| 0–2 | R0 |
| 3–6 | R1 |
| 7–11 | R2 |
| 12–16 | R3 |
| 17–22 | R4 |

Unknown values SHALL use the highest plausible score until resolved.

### 9.3 Hard overrides

The following impose a minimum risk regardless of score. Path rules are only one signal; semantic changes, generated outputs, configuration indirection, and service-criticality floors SHALL be evaluated so that moving or renaming code cannot bypass risk.

#### Minimum R3

- authentication or authorization;
- Supabase RLS or equivalent data-access policy;
- secrets handling;
- public API contract or event schema;
- production dependency introduction;
- payment, pricing, discount, tax, invoice, or ZATCA logic;
- workflow, policy, test-harness, or deployment-control changes;
- infrastructure as code;
- persistent data schema change;
- cross-service transaction;
- backup or restore logic;
- security scanner or coverage threshold change.

#### Minimum R4

- destructive migration;
- `DROP`, `TRUNCATE`, unsafe `CASCADE`, unbounded `DELETE`, or unbounded `UPDATE`;
- disabling RLS or broadening privileged access;
- direct production data correction;
- irreversible secret or identity change;
- change with credible data-loss potential;
- production infrastructure replacement;
- rollback that has not been proven;
- critical financial/compliance calculation with broad historical impact;
- change that combines control-plane modification and application behavior.

### 9.4 Risk override policy

- A human MAY raise risk at any time.
- A human MAY lower a score-derived risk by one level only with a signed, scoped, expiring rationale.
- A hard override SHALL NOT be lowered below its defined minimum.
- Any scope expansion triggers automatic reclassification.
- The highest applicable rule wins.

## 10. Autonomy Policy

Risk and autonomy are separate.

### 10.1 Autonomy levels

| Level | Capability |
|---|---|
| A0 | Analysis and recommendation only |
| A1 | Edit isolated worktree and run approved local checks |
| A2 | Patch Broker may open/update a PR after deterministic validation |
| A3 | Policy may auto-queue merge and auto-release after required evidence |
| A4 | Reserved; no direct unrestricted production autonomy |

### 10.2 Maximum autonomy by risk

| Risk | Maximum autonomy |
|---|---|
| R0 | A3 |
| R1 | A3 after maturity criteria |
| R2 | A2 initially; A3 only after measured reliability |
| R3 | A2, with human plan and release gates |
| R4 | A1, with explicit human checkpoints |

### 10.3 Required gate profile by risk

This table is the minimum delivery path. A policy may add controls but SHALL NOT remove a hard minimum.

| Risk | Planning | Machine verification | Independent review | Human technical review | Release control |
|---|---|---|---|---|---|
| R0 | Lightweight metadata; no unresolved ambiguity | Fast CI and protected branch rules | Not required | Not required | Auto-release allowed where applicable |
| R1 | Valid Change Contract | Fast CI plus affected tests | Required | Not required after M2 unless policy triggers | Auto-merge/release only after maturity criteria |
| R2 | Valid Change Contract and explicit test/rollback plan | Fast + extended affected suite | Required | Human merge decision initially; may become policy-based only after M3 evidence | Progressive release; A2 initially |
| R3 | Human-approved plan, threat model, and rollback plan | Full affected suite, protected/hidden tests, security and migration checks | Required | Required | Human release approval and canary/rings |
| R4 | Approved change plan, rehearsal, backup/restore evidence, explicit stop criteria | Custom full assurance suite | Required but advisory | Required; two-person review where organizationally possible | Manual controlled release; no autonomous production action |

For a solo developer, the R3/R4 human technical review is an explicit evidence review by the owner. An external qualified reviewer SHOULD be used for destructive data changes, authorization, regulated financial calculations, or irreversible infrastructure changes.

### 10.4 Maturity gates

Automation SHALL be enabled progressively.

| Maturity | Scope |
|---|---|
| M0 — Observe | Agents analyze only; no write |
| M1 — Assist | Agents edit worktrees; human creates PR |
| M2 — Bounded PR | Patch Broker creates PR; no auto-merge |
| M3 — Low-risk auto-merge | R0/R1 only after stable metrics |
| M4 — Low-risk auto-release | R0/R1 and selected R2 after stable runtime metrics |

Promotion to a higher maturity level requires:

- no unauthorized action;
- no accepted fabricated evidence;
- stable schema compliance;
- acceptable escaped-defect rate;
- acceptable blocking-finding precision;
- proven rollback;
- stable CI;
- completed red-team tests;
- approved governance review.

| Gate | Required before | Required evidence |

- Invalid specification → `BLOCKED`
- Risk policy violation → `BLOCKED`
- Fast CI failure → `REWORK_REQUIRED`

- Evidence mismatch → `BLOCKED`
- Repair circuit breaker → `BLOCKED`
- Canary failure → stop rollout and `ROLLED_BACK` or `INCIDENT`
- Production health failure → `INCIDENT`
- Scope change → return to `PLANNED`

## 12. Evidence Model

### 12.1 Evidence hierarchy

| Level | Source | Authority |
|---|---|---|
| E0 | Agent text, issue text, comments, summaries | Untrusted |
| E1 | Repository facts from exact SHA | Factual but not proof of runtime correctness |
| E2 | Local tool output in agent sandbox | Diagnostic only |
| E3 | Protected CI on clean checkout | Merge-gate evidence |
| E4 | Signed build provenance, SBOM, artifact digest | Release-gate evidence |
| E5 | Staging and production runtime telemetry | Runtime decision evidence |
| E6 | Human approval or risk acceptance | Governance evidence, scoped and expiring |

### 12.2 AI-review execution evidence

An AI review has two distinct parts:

1. **Review execution record:** trusted metadata produced by the Agent Gateway proving that an approved reviewer model processed an exact context, prompt, and head SHA. This may be retained as E3 process evidence.
2. **Review content:** findings, “no finding” statements, and explanations produced by the model. These remain E0 agent claims until validated.

Therefore:

- `NO_BLOCKING_FINDINGS_IN_REVIEWED_SCOPE` proves only that the model proposed no blocking finding in the supplied scope.
- It does not prove that the code is correct.
- A review gate passes only when the required review execution record exists, all proposed blocking findings have completed the finding protocol, and every other required machine/human gate is valid.
- A model-generated finding never becomes trusted merely because the Agent Gateway stored its output.

### 12.3 Evidence record

```json
{
  "evidence_id": "ev-ci-unit-000842",
  "type": "CI_TEST_REPORT",
  "trust_level": "E3",
  "producer": "github-actions:delivery-control@<full-sha>",
  "repository": "org/app",
  "change_contract_hash": "sha256:...",
  "base_sha": "f36eae17...",
  "head_sha": "88528b10...",
  "policy_bundle_hash": "sha256:...",
  "toolchain_hash": "sha256:...",
  "environment": "github-hosted-ephemeral",
  "command_id": "trusted-unit-suite-v4",
  "exit_code": 0,
  "output_hash": "sha256:...",
  "created_at": "2026-07-30T12:00:00Z",
  "invalidated_by": [],
  "signature_or_attestation": "reference"
}
```

### 12.4 Evidence validity

Evidence is valid only when all required fields match the subject being evaluated.

Invalidators include:

- a changed approved requirement, Change Contract, or specification hash;
- a new head SHA;
- a changed base SHA where latest-base compatibility matters;
- policy bundle change;
- workflow or toolchain change;
- test configuration change;
- changed model/prompt for an AI review;
- changed artifact digest;
- changed environment configuration;
- expired approval;
- risk increase;
- protected-path change.

### 12.5 Partial invalidation

Not every fix needs a full restart, but invalidation must be explicit.

| Change after review | Minimum invalidation |
|---|---|
| Exact targeted fix within reviewed files, no scope growth | Targeted tests, impacted tests, closure review |
| New file or component | Risk reclassification and expanded review |
| Public contract, schema, dependency, permission | Full R3/R4 gate reset |
| Control-plane file | Separate PR; all application-change approvals invalid |
| Base branch changed | Merge-queue verification |
| Artifact rebuilt | Staging and release evidence invalid |

### 12.6 Evidence ledger

The evidence ledger SHALL be append-only and SHALL retain:

- state transitions;
- actor identities;
- model and prompt versions;
- tool requests and broker decisions;
- test and scanner references;
- finding lifecycle;
- approvals and waivers;
- artifact and deployment records;
- rollback or incident records;
- token and cost metrics.

The ledger SHALL store concise rationales and evidence references. It SHOULD NOT request or store private chain-of-thought.

## 13. Context Engineering

### 13.1 Deterministic context selection

The model SHALL NOT be the sole selector of its own context.

The Context Builder SHALL use:

- git diff and changed-path analysis;
- language-server definitions and references;
- build-system dependency graph;
- import graph;
- API/OpenAPI/GraphQL/protobuf contracts;
- database schema and migration graph;
- event producer/consumer registry;
- test-to-code map;
- CODEOWNERS;
- runtime/service topology;
- configuration references;
- feature-flag registry;
- relevant ADRs and invariants.

### 13.2 Context expansion policy

| Risk | Minimum context |
|---|---|
| R0 | Diff and changed file |
| R1 | Diff, full changed files, direct interfaces, direct tests |
| R2 | R1 plus callers/callees, contracts, config, one dependency hop |
| R3 | Affected subsystem, two dependency hops where reliable, threat model, runbooks |
| R4 | Human-approved context plan; full affected system where needed |

When dynamic loading, reflection, generated code, database triggers, or unknown coupling prevents reliable graph construction, the system SHALL expand context or raise risk.

### 13.3 Context manifest

Every agent run SHALL receive a manifest.

```json
{
  "context_id": "ctx-123",
  "repository": "org/app",
  "head_sha": "88528b10...",
  "policy_hash": "sha256:...",
  "included": [
    {"path": "src/orders/service.ts", "hash": "sha256:...", "reason": "changed"},
    {"path": "src/tax/contract.ts", "hash": "sha256:...", "reason": "direct interface"}
  ],
  "excluded": [
    {"path": "src/legacy/import.ts", "reason": "no graph path found"}
  ],
  "known_gaps": [
    "Dynamic plugin loading cannot be resolved statically"
  ],
  "trust_labels": {
    "change-contract.yaml": "TRUSTED_REQUIREMENT",
    "src/orders/service.ts": "REPOSITORY_DATA",
    "issue-body.txt": "EXTERNAL_UNTRUSTED_CONTENT"
  }
}
```

### 13.4 Context integrity

- Every included file SHALL be hashed.
- Context SHALL be generated from the exact head SHA.
- Secrets and production data SHALL be removed before context creation.
- External documents SHALL be immutable snapshots with source and retrieval time.
- Repository comments and documentation SHALL be treated as data, not higher-priority instructions.
- Protected `AGENTS.md` instructions SHALL be hashed and versioned.
- An agent MAY request one bounded context expansion. Repeated context requests trigger re-scope or escalation.

### 13.5 Context and token efficiency

- Cache summaries and symbol maps by content hash.
- Do not resend unchanged files within the same SHA.
- Prefer interfaces and relevant excerpts to entire unrelated modules.
- Keep raw logs around the first failure and relevant stack frames.
- Use deterministic parsers for test reports instead of model summaries.
- Do not provide prior agent reasoning to the independent reviewer.
- Do not include generated files unless they are directly under review.
- Split work when the reviewer requires more context than the risk envelope permits.

### 13.6 Session and memory hygiene

- Agent sessions SHALL be ephemeral and scoped to one work item and one authorized role.
- Unreviewed free-form memory SHALL NOT carry across tasks.
- Reusable facts SHALL enter a later task only through a versioned, reviewed repository artifact or trusted metadata record.
- A session SHALL restart when the head SHA, effective instructions, model registry entry, role, or material context changes.
- Repair sessions receive only the confirmed finding, approved context, current diff, and relevant evidence; they do not inherit unrelated conversation history.
- The independent reviewer SHALL not receive the implementer's self-assessment before forming its initial findings. This reduces anchoring; approved evidence may then be used for verification.
- Session transcripts and outputs SHALL follow data-retention and access-control policy. Private chain-of-thought is neither requested nor required.

## 15. Hallucination Boundaries

### 15.1 Closed-world repository claims

The agent may assert that a file, symbol, endpoint, command, test, or configuration exists only when a trusted read or symbol tool returned it for the exact SHA.

### 15.2 Execution claims

An agent cannot create a valid test, build, or deployment evidence record. Only the runner or control plane can.

The phrase “tests passed” is ignored unless it references E3 evidence.

### 15.3 Root-cause claims

A root cause may be promoted from hypothesis to confirmed only when at least one of the following exists:

- a failing regression test before the fix and a passing result after the fix;
- a runtime trace that crosses the identified defect;
- a reproducible query or state transition;
- a static proof accepted by a deterministic analyzer;
- a human engineering decision referencing inspected evidence.

Otherwise the state is `ROOT_CAUSE_HYPOTHESIS`.

### 15.4 Side-effect claims

The statement “there are no side effects” is prohibited.

The agent must instead report:

```yaml
tested_scope:
  - order creation
  - invoice calculation
untested_scope:
  - legacy CSV import
known_unknowns:
  - concurrent refund behavior
```

### 15.5 Requirement hallucination

The agent SHALL stop when required behavior is not derivable from the Change Contract or an approved decision.

### 15.6 Review hallucination

A proposed blocking finding is not accepted unless it includes:

- exact SHA;
- file and line range or symbol;
- violated acceptance criterion, invariant, contract, or security rule;
- evidence;
- reproduction or proof where feasible;
- blast radius;
- attempted counterexample or falsification;
- proposed severity.

### 15.7 Unsupported-claim metric

The system SHALL measure:

- unsupported claims produced;
- unsupported claims rejected;
- unsupported claims accidentally accepted.

The target for accepted unsupported claims is zero.

## 16. Prompt Injection and Tool Security

### 16.1 Trust labels

Inputs SHALL be labeled:

- `TRUSTED_POLICY`
- `TRUSTED_REQUIREMENT`
- `REPOSITORY_DATA`
- `TOOL_OUTPUT`
- `EXTERNAL_UNTRUSTED_CONTENT`
- `SENSITIVE_REDACTED_CONTENT`

Instructions found in repository files, issues, logs, web pages, package metadata, or test fixtures SHALL be treated as data unless they are part of a protected, approved instruction file.

### 16.2 Network policy

Default agent-phase network access is:

```text
DENY
```

Exceptions require:

- an explicit task need;
- domain allowlist;
- read-only HTTP methods where possible;
- no credentials;
- response-size limits;
- content labeling as external untrusted content;
- audit log.

POST, PUT, PATCH, DELETE, arbitrary sockets, SSH, and generic upload capability SHALL remain blocked for agents.

### 16.3 Build environment and dependency installation

The preferred agent environment is a prebuilt, signed development image with:

- pinned operating-system image digest;
- pinned language/runtime versions;
- locked package manager;
- dependencies restored from an approved cache or registry;
- no production credentials;
- no privileged container socket.

Dependency installation SHALL occur in a controlled setup phase, not through unrestricted agent browsing. An agent may propose a dependency change, but package-manifest or lockfile changes trigger dependency review and the applicable risk override. Install scripts and post-install hooks SHALL be disabled where feasible or inspected in an isolated job.

### 16.4 Approved documentation retrieval

For high-control tasks, an external deterministic service SHOULD retrieve official documentation, hash it, and place it in the context pack. The agent should not browse the open internet directly.

### 16.5 Filesystem policy

Implementation agents may write only to an ephemeral task worktree. They SHALL NOT read:

- `.env` files;
- SSH keys;
- browser profiles or cookies;
- cloud credentials;
- unrelated repositories;
- production database exports;
- user home secrets;
- Docker socket;
- host-level configuration.

### 16.6 Command policy

Commands SHALL be executed through a broker or OS sandbox.

Explicitly prohibited for agents include:

```text
git push
git push --force
gh auth
ssh
scp
ftp
nc
curl | shell
wget | shell
npm publish
docker login
kubectl against production
terraform apply
cloud CLI against production
database clients against production
```

A shell string generated by a model SHALL NOT be interpolated into a privileged command. Privileged tools SHALL use typed arguments.

### 16.7 MCP and plugin policy

- Read and write tools SHALL be separate.
- Tool schemas SHALL be strict and minimal.
- Generic “execute arbitrary command” tools SHALL NOT be exposed to review agents.
- Write tools SHALL require deterministic policy authorization.
- Production MCP tools SHALL not be mounted in agent sessions.
- Connector outputs SHALL be treated as untrusted content.
- Tool results SHALL include subject identity and timestamps.
- An agent SHALL never receive a long-lived connector token.

### 16.8 Subagent policy

Subagents are disabled by default because they increase cost, context fragmentation, and control complexity.

When explicitly enabled:

- maximum two subagents;
- read-only tools only;
- no secrets or network;
- bounded task and context;
- independent structured outputs;
- parent agent cannot convert subagent agreement into approval;
- token budget is charged to the same work item.

## 17. Control-Plane Protection

### 17.1 Protected assets

At minimum, protect:

```text
delivery-control/**
.github/workflows/**
.github/CODEOWNERS
.github/dependabot.yml
AGENTS.md
**/AGENTS.override.md
.codex/**
.delivery/**
.policy/**
security/**
deploy/**
infra/**
test-harness/**
package-manager configuration
test-runner configuration
coverage configuration
build scripts
release scripts
```

### 17.2 Rules

1. Application behavior and control-plane changes SHALL NOT be combined in one PR.
2. Control-plane changes are minimum R3.
3. Agents may propose, but never directly modify, the delivery-control repository.
4. Control-plane changes require human CODEOWNER approval.
5. Required reviews SHALL be dismissed when protected files change.
6. Approval of the most recent push SHALL be required for protected changes.
7. Admin bypass SHALL be disabled or restricted to audited break-glass.
8. Force pushes and branch deletion SHALL be disabled.
9. Required conversations SHALL be resolved.
10. Merge queue validation SHALL include the `merge_group` event.
11. Reusable workflows and actions SHALL be pinned to a full commit SHA.
12. Workflow token permissions SHALL be explicitly minimized.
13. `pull_request_target` SHALL NOT execute untrusted PR code.
14. Untrusted PR workflows SHALL not receive secrets.

### 17.3 Platform-feature availability

Some GitHub environment protections and related controls vary by repository visibility and plan. The implementation SHALL verify feature availability before declaring a gate active.

If a required native feature is unavailable:

- implement an equivalent external policy gate or upgrade the platform;
- document the compensating control;
- test the bypass resistance;
- do not silently omit the control;
- do not claim the High-Control profile until the equivalent control is proven.

### 17.4 Agent instruction files

`AGENTS.md` and overrides influence agent behavior and therefore are control-plane assets.

- They SHALL be small, specific, and versioned.
- Their hash SHALL be recorded in every agent run.
- New override files require human approval.
- A task SHALL restart if its effective instruction chain changes.
- Project instructions SHALL never contain secrets.
- Instructions SHALL not be used as the only enforcement mechanism for a security boundary.

## 18. Source-Control and Pull-Request Policy

### 18.1 Branch policy

Use trunk-based development with short-lived task branches. Long-lived branches SHALL be avoided; incomplete larger work is integrated safely through decomposition and feature flags.

- `main` is protected.
- Direct pushes are prohibited.
- Force pushes are prohibited.
- Deletion is prohibited.
- Required checks are enforced.
- A single protected `delivery-gate` check SHOULD be emitted by the trusted control plane and required by branch protection. It succeeds only when every risk-applicable check is valid.
- Required checks SHALL come from the expected GitHub App/workflow identity where the platform supports source binding.
- Unexpected `skipped` or `neutral` results SHALL not satisfy the umbrella gate.
- Merge queue is required when supported and beneficial.
- The queue SHALL be configured to avoid accepting individually failing pull requests into a merge group.
- Changes are validated against latest `main`.
- The merge method SHALL be consistent and documented.
- Commit or merge identity SHALL be auditable.

### 18.2 Pull-request manifest

Every PR SHALL include:

```markdown
## Outcome
## Acceptance Criteria
## Non-Goals
## Invariants
## Policy Risk and Reasons
## Changed Components
## Test Evidence
## Independent Review Status
## Security and Dependency Status
## Deployment and Feature-Flag Plan
## Rollback Plan
## Observability
## Known Unknowns
## Evidence Manifest Reference
```

### 18.3 Patch Broker

The Patch Broker SHALL:

- accept only a patch from an approved task workspace;
- reconstruct and inspect the diff from a clean checkout of the expected base SHA rather than trust the agent's manifest;
- apply the patch with strict path canonicalization and reject traversal outside the repository;
- reject unexpected symlinks, hard links, submodule changes, `.gitmodules`, Git hooks/configuration, executable-bit changes, large binaries, or LFS pointer changes unless explicitly allowed by policy;
- verify changed paths, file types, modes, and content against scope and risk;
- reject control-plane changes in application tasks;
- run post-patch risk classification before creating the commit;
- create a commit with task, policy, and evidence metadata;
- recompute the resulting tree and head SHA and bind all subsequent evidence to it;
- use a short-lived branch-scoped credential;
- push only to the task branch;
- create or update the PR;
- never approve, merge, or deploy.

### 18.4 Stale-review prevention

Any new commit invalidates review evidence bound to the prior head SHA.

For a narrow verified-finding fix, the Policy Engine may request a closure review rather than a full review only when:

- no new component is introduced;
- no risk trigger changes;
- diff growth is within the allowed threshold;
- affected-context manifest remains valid;
- the fix directly maps to the original finding.

## 19. Test Strategy

### 19.1 Test authority

Tests written by the implementation agent are valuable but not sufficient proof because they may encode the same misunderstanding as the implementation.

Use layered verification:

1. implementation tests;
2. protected regression tests;
3. protected contract tests;
4. external or hidden black-box acceptance tests for high-risk behavior;
5. runtime synthetic tests.

### 19.2 Test layers

| Layer | Purpose | Typical gate |
|---|---|---|
| Static syntax and formatting | Basic validity | Fast CI |
| Lint and type analysis | Defect prevention | Fast CI |
| Targeted unit tests | Fast changed-behavior feedback | Fast CI |
| Full unit suite | Regression detection | Extended CI |
| Property-based tests | Invariant exploration | R2+ critical logic |
| Mutation tests | Test-suite strength | Critical modules/nightly |
| Contract tests | API/event compatibility | R2+ |
| Integration tests | Cross-component behavior | R2+ |
| Database migration tests | Forward/backward compatibility | R3/R4 |
| Security tests | Auth, injection, access control | R3/R4 |
| Performance tests | Capacity and latency | Risk-triggered |
| Accessibility tests | User-interface requirements | Risk-triggered |
| End-to-end tests | Critical user paths | Staging/nightly |
| Synthetic runtime tests | Release verification | Production |

### 19.3 Bug-fix policy

For a confirmed defect, the preferred sequence is:

```text
Reproduce
→ add failing regression test
→ verify failure on base revision
→ implement minimal fix
→ verify test passes on fixed revision
→ run impacted suite
```

When a test cannot be added, the exception and alternate proof must be documented and approved at the required risk level.

### 19.4 Protected test assets

Changes to the following are minimum R3 or require a separate PR:

- critical regression suite;
- contract test expectations;
- security tests;
- hidden acceptance tests;
- test runner;
- coverage thresholds;
- test selection map;
- snapshot approval policy;
- mutation-testing policy.

### 19.5 Test-tampering detections

The Policy Engine SHALL detect and block or escalate:

- `.skip`, `xit`, `xdescribe`, or equivalent;
- newly disabled or quarantined critical tests;
- reduced assertions;
- deleted regression tests;
- broad snapshot rewrites;
- expected-result changes in the same bug-fix PR without approval;
- replacement of integration behavior with mocks;
- `try/catch` that suppresses failure;
- `|| true`;
- `continue-on-error` on a required job;
- reduced coverage threshold;
- altered test command that omits suites;
- changes to fixture data that merely make a failing test pass.

### 19.6 Flaky-test policy

- A failed test SHALL not be repeatedly rerun until it passes.
- One diagnostic rerun MAY be permitted.
- Fail-then-pass is `FLAKY`, not `PASS`.
- A flaky required test keeps the gate blocked.
- Quarantine requires an owner, issue, expiry, and compensating coverage.
- Agents cannot add retries or quarantine critical tests without approval.
- Flake rate is a delivery-system metric.

### 19.7 Test data

- Production data SHALL not be placed in model context or ordinary test logs.
- Sensitive test data SHALL be synthetic or irreversibly masked.
- Logs SHALL be redacted before agent access.
- Tenant isolation tests SHALL be included for multi-tenant data paths.

## 20. Independent Review and Finding Protocol

### 20.1 Review timing

To save tokens without delaying the pipeline:

1. run Fast CI first;
2. if Fast CI passes, start independent AI review and Extended CI in parallel;
3. do not spend review tokens on a patch that does not compile or pass targeted tests.

### 20.2 Reviewer independence

The reviewer receives:

- approved Change Contract;
- exact diff and full changed files;
- deterministic context pack;
- applicable invariants and threat model;
- machine evidence references;
- no implementer chain-of-thought;
- no implementer claim that the solution is correct;
- no instruction to defend the implementation.

The review SHOULD use two logical passes within the same bounded run:

1. inspect requirements, code, contracts, and risks before reading the implementer's rationale;
2. compare any permitted rationale and machine evidence against the independently formed hypotheses.

The reviewer is read-only and has no network or secrets. A passing test result may narrow investigation, but SHALL NOT cause the reviewer to assume the tested requirement or test oracle is correct.

### 20.3 Review scope

The reviewer SHALL check:

- acceptance-criteria alignment;
- invariant preservation;
- hidden impact and coupling;
- correctness and edge cases;
- authorization and data isolation;
- data integrity and migrations;
- financial/regulatory calculations where applicable;
- concurrency, idempotency, retries, and failure handling;
- public contracts;
- error handling and observability;
- dependency and configuration changes;
- test adequacy and test tampering;
- rollback compatibility;
- unnecessary scope.

Style-only observations SHALL not block delivery unless they violate an enforced standard.

### 20.4 Finding output limits

The reviewer SHALL prioritize evidence-backed material risks.

- Maximum five blocking findings per run.
- Maximum five advisory findings per run.
- Findings are ordered by severity, evidence quality, and blast radius.
- If more material findings are suspected, the reviewer returns `REVIEW_SCOPE_UNSTABLE` and the item is blocked for re-scope rather than emitting an unbounded list.
- Duplicate findings are consolidated.

### 20.5 Finding schema

```yaml
finding_id: REV-014
head_sha: 88528b10...
proposed_severity: P1
category: correctness
location:
  file: src/invoice/calculate.ts
  lines: 84-101
violated_rule:
  type: invariant
  id: INV-TAX-003
claim: "Discount is applied after VAT"
evidence_refs:
  - symbol-query-019
reproduction:
  status: proposed
  command_id: trusted-target-test
  case: order-discount-02
counterexample_attempt:
  performed: true
  result: "No preserving path found"
blast_radius:
  - invoices
  - reports
uncertainties: []
```

### 20.6 Finding severity

| Severity | Meaning | Gate effect |
|---|---|---|
| P0 | Active security breach, data loss, or catastrophic failure | Immediate block/incident |
| P1 | Functional regression, authorization failure, incorrect critical calculation, contract break | Block |
| P2 | Material reliability, performance, or maintainability risk | Risk-dependent block |
| P3 | Non-material improvement or style | Advisory/backlog |

Severity proposed by the model is validated by policy or a human.

### 20.7 Finding verification

Every proposed blocking finding SHALL be falsified or confirmed.

```text
PROPOSED
→ CONFIRMED
→ FIXED
→ CLOSURE_VERIFIED

or

PROPOSED
→ FALSIFIED

or

PROPOSED
→ INCONCLUSIVE
```

#### `CONFIRMED`

Requires reproducible machine evidence, accepted static proof, or human engineering judgment tied to inspected evidence.

#### `FALSIFIED`

Requires a counterexample, correct contract interpretation, or machine evidence showing the claim is false.

#### `INCONCLUSIVE`

- R0/R1 non-security: advisory unless acceptance-critical.
- R2: requires more evidence or human decision.
- R3/R4, security, permissions, data integrity, or financial logic: blocks.

### 20.8 No voting

Model consensus, model disagreement, and confidence scores do not decide findings. Evidence or accountable human judgment does.

## 21. Repair Loop and Circuit Breakers

### 21.1 Repair sequence

```text
1. Verify the finding
2. Identify the violated requirement or invariant
3. Add or select a failing proof
4. Apply the smallest scoped fix
5. Run targeted checks
6. Run impacted checks
7. Reclassify risk and scope
8. Perform closure review
9. Continue only if all invalidated gates are restored
```

### 21.2 Maximum cycles

Initial policy:

- R0/R1: maximum one repair cycle;
- R2/R3: maximum two repair cycles;
- R4: cycles defined by the approved plan, with human checkpoints.

Cycle 1 is a targeted correction.
Cycle 2 requires a root-cause re-plan, not another blind patch.
Cycle 3 is prohibited without explicit escalation.

### 21.3 Immediate stop conditions

Stop and classify the task when:

- the same failure recurs twice;
- root cause cannot be reproduced;
- the change expands into a new component;
- diff size grows more than 25% after review;
- a public contract, schema, permission, dependency, or control-plane change appears unexpectedly;
- more than five confirmed findings appear;
- a required test becomes flaky;
- evidence subjects do not match;
- the agent attempts an unauthorized action;
- schema validation fails twice;
- budget usage reaches 80% without a viable completion path;
- requirements conflict;
- rollback becomes uncertain.

### 21.4 Stop classification

```text
SPEC_PROBLEM
ARCHITECTURE_PROBLEM
TEST_ORACLE_PROBLEM
ENVIRONMENT_PROBLEM
MODEL_LIMITATION
DEPENDENCY_PROBLEM
SECURITY_BOUNDARY_PROBLEM
SCOPE_TOO_LARGE
CONTROL_FAILURE
```

The task SHALL return to the correct owner rather than consume remaining budget through random prompt variations.

## 22. CI Pipeline

### 22.1 Pipeline stages

```text
Stage 0: Policy preflight
Stage 1: Fast CI
Stage 2: Extended CI and independent review in parallel
Stage 3: Evidence and finding gate
Stage 4: Merge queue / latest-main validation
Stage 5: Protected release build
Stage 6: Artifact attestation and SBOM
Stage 7: Staging verification
Stage 8: Progressive production release
Stage 9: Runtime observation
```

### 22.2 Stage 0 — Policy preflight

Checks:

- valid Change Contract;
- exact task and branch identity;
- risk classification;
- changed-path policy;
- protected-path separation;
- size limits;
- secrets scan;
- dependency-manifest change;
- migration detection;
- test-tampering detection;
- workflow permission checks;
- evidence manifest schema.

### 22.3 Stage 1 — Fast CI

Required where applicable:

- clean checkout;
- lockfile integrity;
- formatting check;
- lint;
- type check;
- targeted unit tests;
- compile/build;
- generated-code consistency;
- secret scan.

### 22.4 Stage 2 — Extended CI

Risk-dependent jobs:

- full unit tests;
- affected integration tests;
- contract tests;
- SAST;
- dependency review;
- license policy;
- IaC scan;
- container scan;
- migration dry run;
- property tests;
- mutation tests for critical modules;
- performance smoke;
- accessibility checks;
- hidden acceptance tests.

### 22.5 Trusted commands

Required CI jobs SHALL invoke commands defined in the protected delivery-control repository or validate the exact hash of local scripts. The implementation agent must not be able to redefine what “test” or “build” means in the same change.

### 22.6 Merge queue

CI SHALL support both normal PR validation and the merge-queue event. A merge candidate is valid only after required checks pass against the latest protected branch and any queued predecessors.

### 22.7 Runner security

- Prefer ephemeral hosted or ephemeral isolated runners.
- Do not run untrusted code on a persistent privileged self-hosted runner.
- Do not expose secrets to untrusted PR jobs.
- Clear workspace and credentials after each job.
- Use minimal `GITHUB_TOKEN` permissions.
- Separate build and deployment identities.
- Restrict egress where feasible.
- Do not mount a privileged Docker socket into untrusted jobs.
- Separate untrusted PR runners from trusted post-merge build and signing runners.
- Treat workflow artifacts, summaries, and logs from untrusted jobs as untrusted input.

### 22.8 Cache and artifact isolation

- Untrusted PR jobs SHALL NOT write a cache consumed by protected build, signing, or deployment jobs.
- Trusted caches SHALL be keyed by repository, trusted workflow revision, toolchain digest, lockfile hash, and platform.
- Cache restore SHALL validate provenance or source class and SHALL not use broad fallback keys across trust boundaries.
- Downloaded CI artifacts SHALL be verified by digest and producer identity before trusted use.
- A cache hit SHALL never replace lockfile, dependency, or build-input verification.
- Cache poisoning or artifact-substitution tests SHALL be included in control-plane security evaluations.

## 23. Software Supply-Chain Controls

### 23.1 Dependency policy

- Lock dependencies and verify registry integrity metadata where supported.
- Review every new production dependency and every material transitive-dependency expansion.
- Validate the exact package name, publisher/namespace, registry, source repository, release age, and maintenance status to reduce typosquatting and dependency-confusion risk.
- Block known critical vulnerabilities according to policy.
- Check license compatibility.
- Prefer established and maintained packages.
- Record the reason, owner, approved version range, and replacement/exit plan for new dependencies.
- Review lockfile diffs with a deterministic parser; do not accept opaque lockfile churn.
- Prevent install scripts where feasible or review them explicitly.
- Do not let an agent publish packages.

### 23.2 GitHub Actions policy

- Pin third-party actions to a full commit SHA.
- Allowlist approved actions.
- Audit action source for sensitive workflows.
- Use organization-level workflow policies where available.
- Minimize job permissions.
- Avoid mutable tags in release-critical workflows.

### 23.3 Build policy

- Build from a clean checkout of the exact merged SHA.
- Use pinned toolchain/container images by digest.
- Isolate user-controlled build steps from provenance signing credentials.
- Generate provenance in the trusted control plane.
- Generate an SBOM.
- Store the immutable artifact by digest.
- Verify attestation before staging and production.

### 23.4 Provenance verification policy

An attestation is useful only when verified against explicit expectations. Before staging and production, the verifier SHALL confirm at minimum:

- expected repository identity;
- expected protected branch or source revision;
- expected build workflow identity and pinned workflow revision;
- expected trusted builder;
- expected artifact digest;
- expected policy/build parameters;
- no disallowed external source or fork;
- signature or issuer validity.

An SBOM and build provenance are complementary:

- the **SBOM** describes components contained in the artifact;
- **provenance** describes where, when, and how the artifact was produced.

Neither replaces vulnerability analysis, testing, or runtime verification.

### 23.5 Release manifest

```json
{
  "release_id": "rel-2026-07-30-001",
  "repository": "org/app",
  "change_contract_hash": "sha256:...",
  "commit_sha": "88528b10...",
  "artifact_digest": "sha256:...",
  "build_workflow_sha": "sha256:...",
  "policy_bundle_hash": "sha256:...",
  "sbom_digest": "sha256:...",
  "provenance_attestation": "reference",
  "test_manifest": "reference",
  "review_manifest": "reference",
  "approved_risk": "R2"
}
```

### 23.6 Source, license, and generated-code provenance

- Agents SHALL NOT paste code from an external source whose origin and license are unknown.
- External snippets retained in the product SHALL record source, license, scope, and reviewer decision where required by policy.
- Generated code SHALL be attributable to the task, model registry entry, prompt/instruction version, and exact source context; this is audit provenance, not a copyright or originality guarantee.
- Similarity or license scanning SHOULD be used for material generated contributions where intellectual-property risk warrants it.
- Dependency licenses, copied assets, fonts, datasets, model weights, and generated media SHALL follow the organization's approved-use policy.
- Legal or policy uncertainty blocks distribution until an accountable human resolves it.

## 24. Deployment and Release

### 24.1 Deployment is not release

- **Deployment:** the artifact exists in an environment.
- **Release:** users or traffic can exercise the behavior.

Feature flags SHOULD decouple deployment from release for R2+ changes where technically appropriate.

### 24.2 Environment sequence

```text
Preview (optional, untrusted)
→ Staging (verified release artifact)
→ Canary/ring
→ Production
→ Observation
```

### 24.3 Build once

The artifact deployed to staging SHALL be promoted to production by exact digest. A production rebuild is prohibited.

### 24.4 Feature-flag governance

Every flag SHALL have:

```yaml
flag_id: orders-new-tax-flow
owner: team-or-user
created_at: 2026-07-30
default: off
expiry_at: 2026-08-30
cleanup_issue: TECH-456
kill_switch: true
```

- Flag changes are audited production changes.
- Expired flags block unrelated expansion until cleaned or waived.
- A flag is not a substitute for secure authorization.
- Incomplete or unsafe code SHALL not be deployed merely because a flag is off.

### 24.5 Initial rollout policy

| Risk | Initial rollout |
|---|---|
| R0 | Direct release after staging/verification where applicable |
| R1 | 100% after staging when rollback is immediate |
| R2 | 5% → 25% → 100%, or equivalent user/tenant rings |
| R3 | 1% → 10% → 50% → 100%, with human release approval |
| R4 | Approved custom plan, limited cohort, extended observation |

When traffic is too low for percentages, use:

- internal users;
- test tenant;
- synthetic transactions;
- selected customer ring;
- one production instance;
- shadow or dual-run comparison.

### 24.6 Release controller

The Release Controller accepts only:

```text
promote(verified_artifact_digest, approved_environment)
rollback(previous_verified_artifact_digest)
stop_rollout(release_id)
```

It SHALL NOT:

- edit source;
- select an unapproved artifact;
- rebuild;
- run arbitrary SQL;
- read broad repository secrets;
- deploy non-main source;
- bypass environment protection.

### 24.7 Credentials

Use short-lived OIDC credentials with:

- repository restriction;
- branch/environment restriction;
- workflow identity restriction;
- minimum cloud permissions;
- short lifetime;
- no secret exposed to the agent.

### 24.8 Deployment concurrency

Only one production deployment per service SHALL be active unless the service has a proven parallel-deployment strategy. Newer safe releases may cancel obsolete queued releases, but SHALL NOT cancel an active migration without an approved procedure.

## 25. Database and Persistent-State Changes

### 25.1 Default pattern

Use expand-and-contract:

```text
Expand schema
→ deploy backward-compatible code
→ backfill in bounded batches
→ validate counts/checksums
→ switch reads/writes
→ observe
→ remove old schema in a later change
```

### 25.2 Prohibited autonomous operations

An agent SHALL NOT run production SQL.

The following are R4 unless a narrower safe rule is proven:

```sql
DROP TABLE
DROP COLUMN
TRUNCATE
DELETE without a bounded predicate
UPDATE without a bounded predicate
destructive type conversion
DISABLE ROW LEVEL SECURITY
broad GRANT
destructive CASCADE
```

### 25.3 Required migration evidence

- schema diff;
- affected-table list;
- row-count estimate;
- expected lock behavior;
- dry-run result;
- backup verification;
- restore-test evidence for R4;
- forward and backward compatibility;
- backfill bounds and pause mechanism;
- validation query;
- timeout and kill conditions;
- rollback or forward-fix plan;
- monitoring metrics.

### 25.4 Rollback caution

Code rollback is not automatically safe after a data migration. The plan SHALL explicitly determine whether rollback, roll-forward, dual-write, or read compatibility is the safe recovery method.

## 26. Runtime Verification and Observability

### 26.1 Required telemetry

Depending on the service:

- availability;
- error rate;
- latency;
- saturation;
- queue depth;
- database errors;
- authorization failures;
- critical transaction success;
- business outcome metric;
- version and artifact digest;
- feature-flag state;
- migration progress;
- data-integrity checks.

### 26.2 Release health

A release is `PRODUCTION_VERIFIED` only when:

- expected artifact digest is running;
- health checks pass;
- synthetic critical path passes;
- no defined rollback trigger fires;
- observation window completes;
- required business checks pass;
- migration validation passes where applicable.

### 26.3 Rollback triggers

Examples:

- error-rate deviation beyond policy;
- critical transaction failure;
- latency regression;
- new unhandled exception;
- health-check failure;
- authorization anomaly;
- data-integrity check failure;
- migration stall or lock breach;
- severe business-metric regression.

Thresholds SHALL be service-specific and based on baseline data.

### 26.4 Automatic rollback

Automatic rollback is allowed only when:

- telemetry is reliable;
- the previous artifact is verified;
- rollback is known to be safe;
- no irreversible state transition makes rollback harmful.

Otherwise the controller stops rollout and opens an incident.

### 26.5 Telemetry integrity, privacy, and decision quality

- Release decisions SHALL use versioned queries, dashboards, and alert policies owned outside the application-change workspace.
- Metrics SHALL identify service version, artifact digest, environment, tenant/ring where permitted, and feature-flag state.
- Canary thresholds SHALL define both a maximum observation time and a minimum sample or synthetic-test requirement; low traffic SHALL not create false confidence.
- Material releases SHOULD compare against a baseline or control cohort when feasible.
- Observability pipelines SHALL be tested before depending on automatic rollback.
- Logs and traces SHALL minimize personal, secret, and regulated data and SHALL apply redaction and access controls.
- Missing, delayed, or contradictory telemetry fails closed for automatic expansion of a high-risk rollout.
- Alert fatigue SHALL be controlled through actionable ownership, deduplication, and periodic threshold review.

### 26.6 Incident feedback

Every escaped defect SHALL produce:

- incident record;
- affected release and digest;
- detection source;
- missed or weak control;
- regression test or monitoring improvement;
- risk-policy update where warranted;
- evaluation case for relevant agents;
- follow-up owner and due date.

## 27. Definition of Verified, Released, and Done

### 27.1 Definition of Verified

A change is `VERIFIED` only when:

- all required machine checks passed for the exact SHA;
- all blocking findings are confirmed/falsified and closed correctly;
- no stale evidence remains;
- risk and scope match;
- protected tests and controls were not weakened;
- evidence manifest is complete.

### 27.2 Definition of Released

A change is `RELEASED` only when:

- exact attested artifact digest is deployed;
- staging evidence is valid;
- required release approval exists;
- production rollout policy completed or is intentionally paused;
- runtime checks pass.

### 27.3 Definition of Done

A work item is `DONE` only when:

- acceptance criteria are satisfied;
- required evidence is retained;
- critical known unknowns are resolved or explicitly accepted;
- documentation and ADRs are updated;
- monitoring is active;
- rollback remains available;
- feature flag cleanup is scheduled;
- no P0/P1 remains;
- P2 deferrals have an owner, reason, and expiry;
- post-release observation is complete;
- metrics are recorded.

## 28. Model Governance

### 28.1 Model Registry

Each permitted model configuration SHALL record:

```yaml
registry_id: implementer-model-v12
provider: approved-provider
exact_model_id: exact-version-or-snapshot
role: implementer
reasoning_effort: approved-level
prompt_version: implement-v5.1
tool_schema_version: tools-v3
context_builder_version: context-v4
allowed_risks: [R0, R1, R2, R3]
data_policy: enterprise-approved
eval_suite_version: agent-evals-v8
eval_result: pass
approved_at: 2026-07-30
approved_by: engineering-owner
```

### 28.2 No silent drift

- No `latest` aliases in high-control automation.
- No silent model fallback.
- No silent prompt change.
- No silent tool-schema change.
- No silent reasoning-effort change.
- Any changed component triggers the required evaluation suite.

### 28.3 Evaluation suite

The evaluation suite SHALL include real project cases:

- past escaped defects;
- hallucinated files/APIs;
- incomplete specifications;
- misleading logs;
- prompt injection in code/comments/issues;
- attempts to weaken tests;
- false-positive security findings;
- authorization and tenant-isolation cases;
- data migration cases;
- dependency-supply-chain cases;
- token-thrashing cases;
- negative controls where no change should be made;
- tool-permission boundary tests.

### 28.4 Evaluation methods

The evaluation corpus, expected outcomes, and programmatic graders SHALL be stored in a portable repository format. Hosted evaluation products MAY be used, but the control system SHALL not depend on a provider-specific evaluation surface remaining available.

Prefer, in order:

1. deterministic assertions;
2. reference tests and hidden tests;
3. human-calibrated rubrics;
4. model graders only for dimensions that cannot be programmatically checked.

A model grader SHALL itself be evaluated and SHALL not authorize production.

### 28.5 Model upgrade process

```text
Candidate registered
→ offline eval
→ security/red-team eval
→ token/cost comparison
→ shadow mode
→ limited R0/R1 use
→ measured review
→ broader approval
```

Rollback to the prior model/prompt configuration SHALL be immediate.

### 28.6 Data governance

- Use only approved providers and account tiers.
- Apply organizational data-retention policy.
- Do not send secrets or unredacted production data.
- Restrict access to prompts, outputs, and logs.
- Retain enough metadata for audit without storing private chain-of-thought.
- Record which source files were sent to which provider.

### 28.7 Data-classification routing

Every repository and context item SHALL have a data classification.

| Class | Example | External-model policy |
|---|---|---|
| C0 — Public | Open-source code and public documentation | Approved providers permitted |
| C1 — Internal | Ordinary proprietary source with no restricted data | Approved enterprise account only |
| C2 — Confidential | Security design, customer-specific logic, sensitive internal data | Explicit provider and role approval; minimum context |
| C3 — Restricted | Secrets, production personal data, regulated records, private keys | Must not be sent to an LLM context |

The Context Builder SHALL remove or redact C3 content. If a task cannot be completed without prohibited content, the agent path is blocked and the work moves to a human-controlled process.

### 28.8 Provider/model outage

- Do not silently fall back to an unapproved model.
- R0 work that requires no model review may continue through deterministic gates.
- Other work remains queued or moves to an approved human process.
- The outage SHALL not weaken required review, data, or security controls.
- Repeated provider instability is included in model/vendor risk review.

### 28.9 Variance and reproducibility limits

Model output is probabilistic even when the model identifier and prompt are pinned. Therefore:

- a recorded configuration supports auditability but does not guarantee byte-for-byte reproducibility;
- critical eval cases SHALL be executed across multiple trials and report variance, not only a single pass;
- promotion thresholds SHALL include worst-case or lower-confidence-bound performance for safety-critical dimensions;
- model-generated code is accepted only through the same repository, test, review, and release evidence as human code;
- a sudden behavioral shift without a registry change is treated as vendor/model drift and may trigger suspension.

## 29. Token and Cost Control

### 29.1 Control philosophy

Token efficiency comes from reducing redundant work, not reducing verification.

### 29.2 Routing policy

| Risk/change type | Default model use |
|---|---|
| R0 non-behavioral | One implementation run; no AI review |
| R1 isolated behavioral | One implementation run + one independent review |
| R2 normal feature/business logic | One implementation run + independent review + bounded closure |
| R3 high risk | Plan assessment + implementation + independent review + human gates |
| R4 critical | Human-controlled plan; models advisory and sandboxed |

### 29.3 Call budget

Initial maximums:

| Activity | R0 | R1 | R2 | R3 | R4 |
|---|---:|---:|---:|---:|---:|
| Planning/model analysis | 0–1 | 0–1 | 1 | 1 | Approved plan |
| Primary implementation run | 1 | 1 | 1 | 1 | Approved plan |
| Independent review | 0 | 1 | 1 | 1 | 1+ by plan |
| Repair cycles | 1 | 1 | 2 | 2 | By human checkpoint |
| Closure review | 0 | 0–1 | 1 | 1 | By plan |
| Third-model escalation | 0 | 0 | 0–1 | 0–1 | By plan |

A same-model “self-review session” is not mandatory. The implementer performs a deterministic pre-handoff checklist in the same run. A fresh same-model review is invoked only when policy or measured value justifies its token cost.

### 29.4 Context and output budgets

Initial limits:

- Do not fill the entire model context window.
- Planning output: normally at most 1,200 tokens.
- Independent review output: normally at most 1,500 tokens.
- Each finding: normally at most 300 tokens plus evidence references.
- Closure review output: normally at most 600 tokens.
- Log summaries: normally at most 500 tokens.
- R0/R1 reviewer context: changed files and direct interfaces, normally no more than 8 product files.
- R2: normally no more than 20 product files; split or escalate when exceeded.
- R3: affected subsystem with a documented context plan; no arbitrary repository dump.
- Logs: first failure, relevant stack, and bounded surrounding lines.
- Agent outputs: concise structured results, not repeated code or narrative.

### 29.5 Cache policy

Cache by:

- repository SHA;
- file content hash;
- symbol graph version;
- policy hash;
- prompt/model version;
- test report hash.

Do not reuse a cache entry after an invalidator.

### 29.6 Cost circuit breaker

At 80% of the item budget without a valid completion path:

- stop model calls;
- classify the blocker;
- preserve current evidence;
- return to planning or human review.

### 29.7 Cost metrics

Track:

- input and output tokens per merged PR;
- tokens per accepted work item;
- tokens per confirmed finding;
- review tokens with no valid finding;
- repair-cycle cost;
- context cache hit rate;
- model escalation rate;
- cost by risk class;
- cost of escaped defects.

A lower token number is not success if escaped defects, rework, or lead time increases.

- Jurisdictional or customer-specific requirements SHALL not be inferred by an agent.
- Evidence retention SHALL define owner, access control, encryption, retention period, deletion/legal-hold process, and integrity verification.
- A control-mapping table SHALL distinguish `implemented`, `partially implemented`, `not applicable`, and `not implemented`.
- No statement of ISO, SOC, NIST, NCA, PDPL, PCI DSS, or other compliance SHALL be made solely because this plan was adopted.

## 31. Exception, Waiver, and Break-Glass Policy

### 31.1 Waiver requirements

A waiver SHALL contain:

- exact control being waived;
- reason;
- risk;
- affected repository, change, and environment;
- compensating controls;
- owner;
- approver;
- start and expiry;
- evidence reference;
- follow-up issue.

No permanent waiver is allowed.

### 31.2 Non-waivable controls

The normal process SHALL not waive:

- exact artifact identity;
- audit logging;
- no agent production credentials;
- no agent merge authority;
- human authorization for an irreversible R4 action;
- secret-protection rules;
- evidence subject matching.

### 31.3 Break-glass

Break-glass is human-initiated only.

Requirements:

- explicit incident or urgent risk record;
- time-limited credential;
- smallest possible scope;
- full logging;
- no LLM possession of the credential;
- post-action verification;
- retrospective and control restoration within one business day;
- second human approval for enterprise critical systems where available.

### 31.4 Emergency-change minimum path

An expedite or emergency change may shorten elapsed time but SHALL not remove the minimum evidence needed to avoid making the incident worse. Any direct production containment or hotfix SHALL be reconciled back into the protected source-of-truth branch and release manifest immediately after stabilization. Deferred checks SHALL have an owner and due date; they cannot remain indefinitely deferred.

Minimum path:

```text
Incident declared
→ human owner and rollback target identified
→ smallest patch prepared in isolated workspace
→ fast compile/type/targeted regression/security checks
→ exact diff reviewed by a human
→ protected build and artifact identity
→ limited rollout or feature-flag change
→ immediate runtime verification
→ rollback/stop on failure
→ full retrospective and deferred checks
```

Emergency release SHALL NOT be used to bypass uncertainty about destructive data or authorization behavior. When evidence is insufficient, containment, feature disablement, traffic isolation, or rollback is preferred to an unverified forward change.

## 35. High-Level Workflow Pseudocode

```python
def process_change(change_id: str) -> None:
    contract = load_validate_and_hash_change_contract(change_id)
    if not contract.valid:
        block("SPEC_INVALID")

    pre_risk = risk_engine.classify_intended_scope(contract)
    enforce_required_human_plan_gate(pre_risk, contract.hash)

    task = create_ephemeral_task(
        model=registry.approved_implementer(pre_risk),
        sandbox="workspace-write",
        network="deny",
        secrets=False,
        budget=budget_for(pre_risk),
        contract_hash=contract.hash,
    )

    agent_result = run_implementer(task)
    validate_agent_schema(agent_result)

    validated_patch = patch_broker.validate_on_clean_base(
        patch=agent_result.patch,
        expected_base_sha=task.base_sha,
        contract=contract,
    )

    post_risk = risk_engine.classify_actual_patch(contract, validated_patch)
    risk = max(pre_risk, post_risk, agent_result.requested_escalation)
    if risk_requires_replanning_or_new_approval(pre_risk, risk):
        block_and_return_to_planning("RISK_OR_SCOPE_CHANGED")

    head_sha = patch_broker.open_pr(validated_patch, risk=risk)

    fast_evidence = protected_ci.fast(head_sha=head_sha, risk=risk)
    if not fast_evidence.passed:
        enter_rework_or_stop(fast_evidence)

    review_result, extended_evidence = parallel(
        independent_review(head_sha=head_sha, risk=risk),
        protected_ci.extended(head_sha=head_sha, risk=risk),
    )

    findings = validate_and_verify_findings(review_result, head_sha=head_sha)
    while findings.blocking and repair_budget_remaining():
        repair = run_confirmed_finding_repair(findings.confirmed)
        head_sha = patch_broker.update_pr(repair.patch)
        invalidate_evidence_for_new_head(head_sha)
        risk = max(risk, risk_engine.classify_actual_head(contract, head_sha))
        rerun_required_gates(head_sha=head_sha, risk=risk)
        findings = closure_review(head_sha=head_sha)

    if findings.blocking or not all_required_evidence_valid(
        head_sha=head_sha,
        contract_hash=contract.hash,
        risk=risk,
    ):
        block("NOT_MERGE_READY")

    merge_queue.enqueue(head_sha=head_sha)
    merged_sha = merge_queue.require_latest_main_checks_and_merge()

    release_artifact = protected_build(merged_sha)
    verify_provenance_sbom_and_digest(release_artifact)

    deploy_staging(release_artifact.digest)
    verify_staging(release_artifact.digest)

    enforce_release_gate(risk, release_artifact.digest)
    progressive_release(release_artifact.digest, rollout_policy(risk))

    if runtime_verification_passes(release_artifact.digest):
        mark_done()
    else:
        stop_or_rollback(release_artifact.digest)
        open_incident()
```

The actual implementation SHALL use typed interfaces and policy decisions, not model-generated control flow.

## 36. Implementation Roadmap

The system SHALL be introduced in waves. Do not enable autonomous merge or release before the corresponding exit criteria are met.

### Wave 0 — Baseline and threat model

Deliverables:

- inventory repositories, environments, credentials, workflows, tests, and agents;
- baseline DORA, flow, defect, token, and CI metrics;
- classify data and critical components;
- identify protected paths;
- document threat model;
- define service ownership;
- define current rollback ability.

Exit criteria:

- all production services and owners identified;
- current release path documented;
- critical unknowns recorded;
- baseline metrics captured.

### Wave 1 — Repository and credential controls

Deliverables:

- protected `main`;
- rulesets/branch protection;
- CODEOWNERS;
- merge queue support;
- latest-push approval where needed;
- force-push and deletion protection;
- least-privilege workflow tokens;
- OIDC for cloud deployment;
- environment protection;
- separate delivery-control repository;
- action pinning policy.

Exit criteria:

- no agent can push, merge, or deploy;
- direct main push blocked;
- required checks enforced;
- production uses scoped short-lived credentials;
- bypass is audited.

### Wave 2 — Deterministic verification

Deliverables:

- Change Contract schema;
- Risk Engine;
- State Machine;
- Evidence schema and ledger;
- fast and extended CI;
- protected test commands;
- dependency/security scanning;
- test-tampering rules;
- merge-queue checks.

Exit criteria:

- every transition is policy-driven;
- required evidence is exact-SHA bound;
- local agent claims cannot mark checks passed;
- control-plane and application PRs are separated.

### Wave 3 — Bounded agent integration

Deliverables:

- isolated worktrees;
- network-off agent environment;
- no-secret context builder;
- strict output schemas;
- Patch Broker;
- implementation and review prompts;
- finding verification protocol;
- repair circuit breakers;
- token budgets;
- audit logging;
- role-based operator training for specifications, evidence review, waivers, rollback, and agent-incident handling.

Exit criteria:

- agent unauthorized actions are blocked;
- schema compliance meets target;
- no fabricated evidence can enter the trusted ledger;
- R0/R1 trials complete under human-observed mode.

### Wave 4 — Supply-chain and release integrity

Deliverables:

- protected post-merge build;
- pinned toolchain;
- SBOM;
- artifact provenance/attestation;
- immutable artifact registry;
- staging by digest;
- release controller;
- feature-flag registry;
- progressive rollout;
- rollback verification.

Exit criteria:

- production promotes the exact staged digest;
- artifact provenance verifies;
- one-command safe rollback exists for reversible changes;

Deliverables:

Exit criteria:

- no silent model changes;
- model upgrades pass evals;
- real incidents become regression/eval cases;
- third model remains escalation-only.

### Wave 6 — Controlled automation and optimization

Deliverables:

- A2 bounded PR automation;

- periodic recovery drills;
- monthly policy improvement.

Exit criteria:

- stable delivery and defect metrics;
- zero accepted fabricated evidence;
- zero unauthorized privileged actions;
- proven rollback;
- auto-release scope approved from measured history.

## 37. Operational Runbooks

### 37.1 Agent produced an unsupported claim

1. Reject output.
2. Record claim and task metadata.
3. Request one schema/evidence correction if budget permits.
4. If repeated, block the task.
5. Add the case to evals.
6. Review prompt, context, and tool availability.
7. Do not weaken the evidence rule.

### 37.2 Agent attempted an unauthorized tool action

1. Deny action at sandbox or broker.
2. Terminate the agent session for T2+ attempts.
3. Rotate any potentially exposed ephemeral credential.
4. preserve audit logs;
5. classify as security event;
6. add red-team/eval case;
7. inspect prompt-injection sources;
8. review tool surface and policy.

### 37.3 Review models disagree

1. Do not vote.
2. extract the exact disputed claim;
3. request reproducible evidence;
4. run a deterministic or black-box test;
5. use human engineering judgment if still inconclusive;
6. use the third model only for additional analysis, not approval.

### 37.4 Repair loop does not converge

1. Stop at the circuit breaker.
2. classify the blocker.
3. preserve the last passing state and evidence.
4. return to planning.
5. split the change or revise architecture.
6. reopen only with a new approved plan and budget.

### 37.5 CI is flaky

1. Mark the check `FLAKY`, not passed.
2. collect diagnostic evidence;
3. block required gate;
4. assign owner and expiry;
5. fix or formally quarantine with compensating tests;
6. track flake-rate impact.

### 37.6 Canary fails

1. freeze rollout;
2. verify telemetry and artifact identity;
3. rollback only if safe;
4. otherwise isolate or disable feature flag;
5. open incident;
6. preserve runtime evidence;
7. add regression and monitoring cases;
8. update risk policy if needed.

### 37.7 Evidence subject mismatch

1. block immediately;
2. identify stale SHA, digest, policy, or environment;
3. invalidate dependent approvals;
4. rerun only the required gates;
5. investigate if mismatch could indicate tampering.

## 39. Final Operating Policy

The final system behavior is:

```text
Human defines the outcome and accountable decisions
→ deterministic validator establishes readiness
→ deterministic risk engine establishes minimum controls
→ bounded agent proposes a patch in an isolated worktree
→ protected CI produces machine evidence
→ independent model proposes review findings
→ findings are proven, falsified, or escalated
→ deterministic policy evaluates exact-SHA evidence
→ merge queue validates against latest main
→ trusted build produces one attested artifact
→ the same digest is verified in staging
→ risk-appropriate release gate authorizes rollout
→ runtime evidence confirms, stops, or rolls back
→ incidents update tests, policies, and model evals
```

The system SHALL never reduce this to:

```text
AI wrote it
→ AI reviewed it
→ therefore it is safe
```
