# النقد اللاذع قبل إصلاح ZTAD Mesh 4.2.0

## الحكم

النسخة التي سبقت هذا الإصلاح كانت **أقوى في الوصف من التنفيذ**. امتلكت مكونات جيدة، لكنها لم تستحق وصف «Mesh تلقائية كاملة». لو شُغّلت بصلاحيات واسعة اعتمادًا على التقارير السابقة، لكان ذلك قرارًا غير منضبط.

## العيوب الحاسمة التي وُجدت

1. **إصدارات مذكورة بلا حزمة فعلية:** ملفات 4.0.0 التي سبق الإعلان عنها لم تكن موجودة في مساحة العمل. المصدر الحقيقي كان 4.1.0 بوثائق 2.0.0. هذا خلل ثقة وإدارة إصدار، لا مجرد تسمية.
2. **التوثيق منفصل عن الواقع:** README وتقارير التحقق ادعت بنية أوسع من المسار الإلزامي في الكود، وأظهرت أرقامًا قديمة للمهارات والسياسات.
3. **Mesh جزئية:** Router وDAG وProviders وWorktrees كانت موجودة، لكن بعض العلاقات بينها اختيارية. كان من الممكن تشغيل أجزاء منفصلة ثم تمثيلها كأتمتة كاملة.
4. **تعريف Method مكرر:** تعريف داخل Class كان يطغى على تعريف آخر بصمت؛ Python لم يفشل، والاختبارات القديمة لم تكتشفه. هذا يثبت أن نجاح الاختبارات لم يكن كافيًا لفحص البنية.
5. **لا Entry point عملي موحد في الأصل:** لم يكن هناك Autopilot واضح يجمع الفهرسة والتخطيط والتوجيه والعمل والتحقق والمراجعة في مسار واحد غير قابل للتجاوز.
6. **نقل المعرفة ناقص:** ترتيب عقد DAG لا يعني أن مخرجات Scouts تصل إلى Planners أو Reviewers. كانت الموازاة معرضة لأن تصبح مجموعة مهام لا تتعلم من بعضها.
7. **المراجعة قبل مرشح حقيقي:** Patches لم تكن دائمًا تندمج في Candidate commit واحد وتُفحص قبل المراجعة. ربط القرار بالـSHA كان لذلك ناقص الدلالة.
8. **مخرجات Provider داخل Worktree:** المسار الافتراضي لبعض نتائج النماذج كان يمكن أن يضيف ملفات تشغيل إلى Patch التطبيق نفسه أو يسبب Scope violation.
9. **Benchmark يلوث المشروع:** Benchmark runs لم تكن تفرض Artifact directory خارجيًا؛ كان يمكن أن تنشئ `.delivery` داخل مستودع القياس.
10. **إعادة تشغيل Artifact قديم:** وجود ملف نتيجة سابق لم يكن محميًا بما يكفي في كل المسارات، ما يفتح باب خلط نتيجة قديمة بتشغيل جديد.
11. **Provider مفضل كنقطة فشل:** Preference كانت معرضة لأن تصبح اعتمادًا صلبًا بدل ترجيح قابل للسقوط إلى بديل مؤهل.
12. **Freshness ناقصة للـBenchmark:** تغير مجموعة حالات القياس لم يكن دائمًا يبطل القياسات القديمة عبر CLI.
13. **Benchmark واحد يمكن أن يطغى:** قياس محدود يمكن أن يستبدل prior بصورة مبالغ فيها ويحوّل Noise إلى قرار توجيه.
14. **Catalog يقبل قيمًا غير منطقية:** قبل التشديد كان يمكن قبول Tier/Sandbox/Reasoning غير مدعوم أو Reliability خارج المجال وتكلفة غير موجبة.
15. **الـRisk لا يعاد حسابه من التنفيذ:** الخطة قد تبدأ R2 ثم يكتب Worker Migration مدمرة؛ من دون Actual-diff classification يصبح Review plan الأصلي غير كافٍ.
16. **Session identity قابلة للتمرير:** موافقة تعتمد على Session ID يقدمه المستدعي أضعف من ربطها بسجل Model run مخزن.
17. **GitHub PR flow غير موثوق:** محاولة استخدام JSON في مسار إنشاء PR لم تكن مطابقة للسلوك العملي المتوقع؛ صُححت إلى Create ثم View.
18. **Stop hook معرض للحبس:** Hook يحاول إبقاء الجلسة مستمرة قد يتحول إلى Loop. الاستمرارية يجب أن يملكها Scheduler، لا أن يمنع Codex من التوقف إلى الأبد.
19. **لا ضمان Process restart:** SQLite تحفظ الحالة، لكنها لا تعيد تشغيل عملية ماتت. الادعاء بـ«يستأنف وحده» يحتاج Service manager خارجيًا.
20. **Coverage غير كافية للأجزاء الأخطر:** المتوسط كان مقبولًا ظاهريًا، لكن Providers/Hooks/Host/Platform paths أقل اختبارًا من محركات البيانات المحلية.
21. **Hosted controls غير مثبتة:** وجود GitHub adapter أو Progressive delivery policy لا يثبت Rulesets أو Merge Queue أو Canary أو Rollback في حساب المستخدم.
22. **SQLite ليست HA:** المنظومة Durable على Host واحد، وليست Queue موزعة لعدة أجهزة أو مناطق.
23. **لا يمكن ضمان “كل شيء مهما حدث”:** Credential غائب أو Provider متوقف أو متطلب متناقض لا تحله كثرة النماذج. أفضل سلوك هو احتواء المهمة واستمرار بقية الطابور.

## السبب الجذري

النسخة كانت تخلط بين ثلاثة أشياء مختلفة:

- وجود Component؛
- ربط Component داخل المسار الإلزامي؛
- إثبات Component على Host الحقيقي.

وجود ملف أو Class أو Policy لا يعني أنه مستخدم، ونجاح Test محلي لا يعني أن منصة خارجية تطبق الضبط.
